# Протокол «Пульт» v1

Транспорт: WebSocket (`wss://<signaling>/ws`), сообщения — JSON, поле `t` = тип.
Всё, что идёт через сервер, — только сигналинг. Содержимое экрана идёт напрямую по WebRTC (DTLS-SRTP).

Ключевой принцип: **сервер не знает секрет пары и не может подменить собеседника.**
Взаимная аутентификация HMAC привязана к отпечаткам DTLS обеих сторон, поэтому
подмена SDP на сервере ломает проверку MAC и сессия не поднимается.

---

## 1. Сущности

| Что | Что это | Кто знает |
|---|---|---|
| `pairId` | 16 случайных байт (base64url), публичный идентификатор пары — ключ маршрутизации | бабушка, внук, сервер |
| `pairSecret` | 32 случайных байта, общий секрет пары | **только устройства** |
| `deviceId` | 16 случайных байт, идентификатор устройства | владелец, сервер |
| `role` | `grandma` \| `helper` | — |
| `journalToken` | `HMAC(pairSecret, "pult/v1/journal")` — доступ к журналу сессий | устройства; сервер хранит только SHA-256 от него |

`pairId`, `pairSecret` создаются на телефоне бабушки в момент спаривания и передаются
внуку **только вблизи** (NFC / QR), никогда через сеть. См. `docs/security.md`.

## 2. Подключение

```
C→S  {"t":"hello","v":1,"pairId":"…","role":"grandma","deviceId":"…",
      "journalTokenHash":"…"}            // hash — необязательно, при первом hello регистрирует журнал
S→C  {"t":"hello-ok","serverTime":1730000000000,"peerOnline":false,
      "iceServers":[{"urls":["stun:…"]},{"urls":["turn:…"],"username":"…","credential":"…"}]}
S→C  {"t":"peer-state","online":true}    // при каждом изменении присутствия второй стороны
```

- До `hello` любое другое сообщение → `error{code:"not-authenticated"}` и разрыв.
- Одна пара — один сокет на роль. Новый `hello` той же ролью вытесняет старый
  (`error{code:"replaced"}` старому сокету): смена сети у бабушки не должна оставлять «призрака».
- Keepalive: `{"t":"ping"}` → `{"t":"pong"}`. Сервер сам шлёт ws-ping каждые 25 с
  и закрывает сокет, не ответивший на два подряд.

Присутствие («бабушка в сети») — это факт живого сокета, ничего больше.

## 3. Запрос помощи и согласие — сценарий 1-2-3

Инициатива у внука, решение — за бабушкой. Её единственное действие: «Разрешить».

```
helper   →S   {"t":"help-request","note":"перезвоню, покажу почту"}   // note необязателен, ≤60 симв.
        S→    {"t":"help-request-sent","sessionId":"…","peerOnline":true}   → helper (подтверждение)
        S→    {"t":"help-request","sessionId":"…","from":"helper","at":…}   → grandma
                                                 // если grandma офлайн — FCM high-priority push,
                                                 // приложение просыпается и показывает запрос
grandma  →S   {"t":"consent-granted","sessionId":"…"}   → helper     // нажата «Разрешить»
        либо  {"t":"consent-denied","sessionId":"…","reason":"declined"}
```

`help-request-sent` приходит только помощнику: из него он узнаёт `sessionId` и то,
онлайн ли телефон бабушки. `peerOnline:false` — не ошибка: запрос остаётся висеть и
будет доставлен, когда её приложение проснётся от push и пришлёт `hello`.

Телефон бабушки регистрирует токен для пробуждения:
`{"t":"register-push","token":"<FCM registration token>"}` — от роли `helper` игнорируется.

`sessionId` выдаёт сервер (16 байт base64url). Он же — контекст всех дальнейших сообщений;
сообщение с чужим/устаревшим `sessionId` отбрасывается.

- Запрос живёт **90 секунд**. Нет ответа → сервер шлёт обеим сторонам
  `session-end{reason:"no-answer"}`, запрос с экрана бабушки исчезает.
- `help-request` от роли `grandma` сервер не маршрутизирует: инициировать может только помощник.
- `consent-granted` от роли `helper` сервер не маршрутизирует: согласие даёт только бабушка.
- Даже подделанное сервером `consent-granted` ничего не даёт: захват экрана запускает
  устройство бабушки по локальному нажатию, а не по сообщению из сети (см. §4, шаг 7).

### Ограничение частоты запросов (защита от навязчивости)

Инициатива у помощника — значит, он технически может дёргать бабушку бесконечно.
Поэтому сервер ограничивает:

- не более **5** `help-request` в час на пару и не более **3** подряд без ответа;
- «тихие часы» (по умолчанию 22:00–08:00 в таймзоне бабушки): запрос доставляется
  без звука и без всплывающего окна, только строкой в шторке;
- превышение → `error{code:"too-many-requests"}` помощнику; бабушке ничего не показывается;
- отклонённые запросы и запросы без ответа **тоже** пишутся в журнал (§7) — семья видит,
  как часто помощник дёргает бабушку.

Настройки «Не беспокоить» и лимиты меняются только на устройстве бабушки.

## 4. Взаимная аутентификация пары (привязка к DTLS)

Начинается только после `consent-granted`. Порядок фиксирован: предлагает соединение
**внук**, отвечает **бабушка**, последнее слово (пускать или нет) — за телефоном бабушки.

```
helper   →  {"t":"offer","sessionId":"…","sdp":"…","nonceH":"<16 байт b64url>"}
grandma  →  {"t":"answer","sessionId":"…","sdp":"…","nonceG":"…","macG":"…"}
helper   →  {"t":"auth-confirm","sessionId":"…","macH":"…"}
```

`fpH` / `fpG` — строка отпечатка DTLS (`a=fingerprint:` из соответствующего SDP,
нормализованная: алгоритм в нижнем регистре, hex в верхнем, формат `sha-256 AA:BB:…`).

```
transcript = "pult/v1/auth" ‖ sessionId ‖ nonceH ‖ nonceG ‖ fpH ‖ fpG      (‖ = разделитель "\n")
macG = HMAC-SHA256(pairSecret, "grandma\n" ‖ transcript)
macH = HMAC-SHA256(pairSecret, "helper\n"  ‖ transcript)
```

- Внук проверяет `macG` перед тем, как показывать поток. Не сошлось → `session-end{reason:"auth-failed"}`.
- Бабушка проверяет `macH` **до старта MediaProjection**. Не сошлось → сессия не начинается,
  захват экрана не запускается вовсе.
- Сравнение MAC — только константное по времени.
- Nonce одноразовые, живут в пределах `sessionId`; повтор `sessionId` сервер не выдаёт.

Что это даёт: сервер видит SDP, но подменить `a=fingerprint` не может — оба MAC считаются
по обоим отпечаткам, а секрета у сервера нет. Классический MITM на сигналинге закрыт.

## 5. ICE и телеметрия соединения

```
{"t":"ice","sessionId":"…","candidate":{"candidate":"…","sdpMid":"…","sdpMLineIndex":0}}
```
Ретранслируется второй стороне без разбора. `candidate:null` (конец сбора) допустим.

TURN-креды выдаются в `hello-ok` по схеме coturn REST:
`username = "<expiryUnix>:<pairId>"`, `credential = base64(HMAC-SHA1(turnStaticSecret, username))`,
TTL по умолчанию 12 ч. Секрет TURN живёт только на сервере и в coturn.

## 6. Сессия: показ экрана, указатель, стоп

После успешной аутентификации открывается WebRTC-datachannel `pult-control` (надёжный, упорядоченный).
Всё управление сессией идёт **в нём**, а не через сервер: сервер о содержимом сессии не знает ничего.

Сообщения datachannel (JSON):

| `t` | Направление | Смысл |
|---|---|---|
| `screen-state` | бабушка → внук | `{"on":true,"w":1080,"h":2340}` — показ начался/закончился |
| `pointer` | внук → бабушка | `{"x":0.42,"y":0.71,"kind":"tap"\|"circle"}` — координаты в долях экрана |
| `pointer-clear` | внук → бабушка | убрать указатель |
| `say` | внук → бабушка | короткая подпись на экране бабушки (до 60 символов) |
| `redact` | бабушка → внук | `{"on":true,"reason":"banking-app"}` — экран погашен для помощника |
| `stop` | любая | завершить сессию немедленно |

Указатель в долях экрана, а не в пикселях: разрешения устройств не совпадают.

Экран гасится (`redact`) телефоном бабушки самостоятельно, по списку банковских пакетов.
Решение принимает **устройство бабушки**, а не помощник — иначе защита ничего не стоит.

## 7. Завершение и журнал

```
любой →S  {"t":"session-end","sessionId":"…","reason":"stopped-by-grandma"}
```

`reason`: `stopped-by-grandma` | `stopped-by-helper` | `declined` | `no-answer` |
`cancelled` | `auth-failed` | `peer-lost` | `timeout` | `error`.

Сервер пишет в журнал **только метаданные**: `sessionId`, `pairId`, кто запросил, дала ли
бабушка согласие, время начала/конца, причину, был ли показ экрана. Никакого содержимого,
никаких кадров. Запросы, на которые бабушка ответила «Не сейчас» или не ответила вовсе,
попадают в журнал наравне с состоявшимися сессиями.

Чтение журнала (доступно всей семье — п.8.4 ТЗ):
```
GET /api/journal?pairId=…      заголовок: X-Journal-Token: <journalToken>
```
Сервер сверяет SHA-256 токена с сохранённым при регистрации пары. Токен выводится из
секрета пары, значит его знают только спаренные устройства, а сервер сам его вычислить не может.

Устройство бабушки ведёт **свой** локальный журнал — он источник истины; серверный журнал
это лишь зеркало для удобства семьи.

## 8. Ошибки

```
{"t":"error","code":"…","message":"…"}
```

| code | Когда |
|---|---|
| `bad-message` | не JSON, нет `t`, превышен размер (64 КБ) |
| `not-authenticated` | сообщение до `hello` |
| `unknown-session` | `sessionId` не активен |
| `peer-offline` | адресат не в сети |
| `replaced` | вытеснен новым сокетом той же роли |
| `rate-limited` | больше 60 сообщений за 10 с |
| `too-many-requests` | превышен лимит `help-request` (§3) |
| `unsupported-version` | `v` ≠ 1 |

## 9. Чего в протоколе нет намеренно

- Нет способа получить экран **без** нажатия «Разрешить» на телефоне бабушки:
  `consent-granted` от роли `helper` сервер не маршрутизирует, а захват экрана
  запускается локальным нажатием, а не сетевым сообщением.
- Нет способа у помощника отменить или обойти запрос согласия — ни настройкой,
  ни флагом в сообщении. «Разрешать всегда» отсутствует как опция.
- Нет удалённого спаривания: `pairSecret` не передаётся ни в одном сообщении.
- Нет «тихого режима»: состояние сессии всегда отражается в постоянном уведомлении и рамке.
- Нет передачи содержимого экрана через сервер.
